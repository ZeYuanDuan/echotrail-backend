# AI 協作文字風格指南（繁體中文）

- **狀態：** 試行
- **版本：** 1.0
- **最後更新：** 2026-08-18
- **適用專案：** 補習班管理系統

## 1. 目的

本指南用來降低 AI 產出中的歧義、贅詞和推測。讀者應能快速判斷：

- 目前確定了什麼。
- 哪些內容仍待確認。
- 誰要採取什麼行動。
- 如何驗證規則或工作已完成。

本指南受 [ASD-STE100 Simplified Technical English](https://www.asd-ste100.org/) 的精神啟發。它不是 ASD-STE100 的官方翻譯，也不代表產出符合 ASD-STE100。

本指南調整了原始草稿中的硬性字數和固定譯名規則。中文的字數不能直接對應英文的單字數。為了縮短句子而刪除條件、例外或不確定性，會改變原意。**清楚和正確優先於最短。**

## 2. 適用範圍

AI 新增、改寫或整理下列內容時，應遵守本指南：

- 業務規格和驗收條件。
- GitHub issue、Pull Request 和交接說明。
- 會議結論、決策摘要和待決問題。
- 操作步驟、錯誤分析和狀態報告。
- 給其他 Agent 的指令或輸入。
- 人類會閱讀的程式碼註解和錯誤說明。

下列內容不要求改寫成本文風格：

- 程式碼識別字、指令、路徑和 API 欄位。
- 原始錯誤訊息、法規原文、外部引文和歷史資料。
- 需要保留語氣的行銷、創作或對外溝通內容。
- 工具自動產生且不供人閱讀的資料。

引用原文時，保留原文。另以中文說明，不要直接改寫引用內容。

## 3. 分層治理

本專案採用分層治理。每一層只負責一種工作。

| 層級 | 保存位置 | 責任 |
|---|---|---|
| 入口提示 | Repo 根目錄的 `AGENTS.md`；需要時也包含其他 Agent 的入口文件 | 提示風格指南的位置、適用時機和預設模式。不要複製完整規則。 |
| 正典規範 | 本文件 | 定義跨文件共用的寫作規則。 |
| 文件契約 | 各文件範本、目錄 `README.md` | 定義規格、issue、會議紀錄等文件的必要欄位。 |
| 執行檢查 | 個別 Skill、自動檢查或審查清單 | 在特定流程中套用必要規則，並回報違規內容。 |

目前由 `AGENTS.md` 和 `CLAUDE.md` 提供入口提示。兩個入口檔應保持精簡，並維持相同規則：

- 連結本指南，不複製完整內容。
- 指定嚴格模式和一般模式的適用範圍。
- 提醒 Agent 不得為了縮短文字而改變原意。
- 說明知識治理文件是目標架構，不能據此自行遷移。

若入口提示需要調整，應同時更新 `AGENTS.md` 和 `CLAUDE.md`。

Skill 不應複製整份指南。Skill 只需寫明：

- 何時啟用指南。
- 使用哪一種模式。
- 該流程額外要求的欄位。
- 輸出前要執行的檢查。

例如，未來若調整 `project-file-issue`，該 Skill 應管理 issue 的欄位和建票流程。本指南仍是文字表達的正典。

### 3.1 規則衝突時的優先順序

若規則互相衝突，依下列順序處理：

1. 保留事實、原意、安全條件、法規要求和資料完整性。
2. 遵守專案業務規則與該文件的格式契約。
3. 遵守本指南。
4. 最後才考慮縮短文字或統一語氣。

若無法同時遵守，保留較重要的內容，並指出衝突。不要自行刪除條件。

## 4. 兩種寫作模式

### 4.1 嚴格模式

下列內容使用嚴格模式：

- 業務規則、驗收條件和權限規則。
- 操作步驟、警告和錯誤訊息說明。
- Agent 指令、工具說明和自動化輸入。
- issue 中的範圍、完成條件和待確認事項。

嚴格模式要求：

- 一個術語只表示一個概念。
- 一個句子只表達一個主要命題。
- 一個步驟只要求一個主要動作。
- 明確寫出行為主體、條件、動作和結果。
- 完整保留數量、時間、範圍、例外和不確定性。
- 不以暗示或上下文補足必要資訊。

### 4.2 一般模式

下列內容使用一般模式：

- README、背景說明和設計討論。
- 會議脈絡、PR 說明和工作摘要。
- 對人的一般回覆。

一般模式仍須保留原意、明確標示不確定性，並避免冗長句。它可以保留自然語氣，不要求每個詞都固定成唯一寫法。

同一份文件可混用兩種模式。例如，issue 的背景使用一般模式，範圍和完成條件使用嚴格模式。

## 5. 核心規則

### 5.1 先理解，再改寫

改寫前，先找出原文中的：

- 事實。
- 要求強度。
- 適用範圍。
- 前置條件。
- 例外。
- 數量和時間。
- 不確定性。

改寫後逐項核對。不得新增原文沒有的原因、頻率、機制或結論。

### 5.2 保留要求強度

「可能失敗」不能改成「會失敗」。「建議處理」不能改成「必須處理」。

在規範性段落中，使用下列詞表示要求強度：

| 用詞 | 意義 |
|---|---|
| 必須 | 不遵守即不符合要求。 |
| 不得 | 明確禁止。 |
| 應 | 原則上要遵守；偏離時要說明理由。 |
| 不應 | 原則上要避免；採用時要說明理由。 |
| 可 | 允許選擇，不表示偏好。 |

這組用詞只用於規範性內容。一般說明仍可使用「建議」「預計」或「傾向」，但要說明它們是建議、計畫或偏好，不是既定規則。

### 5.3 不虛構因果

只有證據支持因果關係時，才能寫「因為 A，所以 B」。

若只有時間上的先後或關聯，寫出觀察結果：

> 部署後，錯誤率從 2% 增加到 8%。目前尚未確認部署是否為原因。

若仍在排查，標示為「推測」或「假設」，不要寫成根因。

### 5.4 一個概念使用一個名稱

同一文件中，不要輪流使用多個詞指稱同一個概念。例如，不要交替使用「承辦人」「業務人員」「使用者」表示同一角色。

業務詞彙以 [P0 通用語言](../../P0_業務規則與通用語言/P0_通用語言.md) 為正典。若正典沒有該詞：

1. 先選擇最具體的現有名稱。
2. 在第一次出現時定義。
3. 若該詞會跨文件使用，再提議加入通用語言。

不要建立跨專案的固定翻譯表。像 `repository`、`commit` 和 `log` 等詞，應依團隊慣例和讀者理解選擇寫法。

### 5.5 寫出主體和動作

優先使用「主體＋動作＋受詞」：

- 好：`ConfigLoader` 讀取設定檔。
- 差：設定檔會被讀取。
- 差：進行設定檔的讀取。

若執行者未知、不重要或刻意隱藏，可使用被動句。不要為了形式而猜測執行者。

### 5.6 條件在前，結果在後

先寫適用條件，再寫動作或結果：

> 若公文尚未生效，系統保留目前狀態。

不要把關鍵條件放在句尾，讓讀者先形成錯誤理解。

### 5.7 一句一個主要命題

一個句子可包含必要條件，但不要同時加入第二個結論、例外和修訂歷史。

出現下列情況時，應拆句或改用列表：

- 一句內有 3 個以上的完整動作。
- 讀者需要回頭判斷「其」「該」「前者」指什麼。
- 同一句同時描述現況、歷史和待決問題。
- 條件或例外的適用對象不清楚。

句長是審查訊號，不是自動違規：

- 嚴格模式的句子超過約 50 個中文字時，重新檢查是否能安全拆分。
- 一般模式的句子超過約 80 個中文字時，重新檢查段落結構。
- 程式碼、網址、路徑和不可拆的正式名稱不計入門檻。

若拆句會破壞條件關係或刪除精度，保留較長的句子。

### 5.8 結論在前

段落先寫讀者需要知道的結果，再補理由、證據和限制。

狀態回報的第一段應先說明：

- 已完成什麼。
- 尚未完成什麼。
- 是否需要讀者決定或採取行動。

不要先敘述完整工作過程，最後才揭露結論。

### 5.9 具體且可驗證

不要用形容詞代替證據：

| 模糊寫法 | 可驗證寫法 |
|---|---|
| 效能更好 | 查詢時間從 120 ms 降到 45 ms。 |
| 已妥善處理 | 已新增 3 個驗收情境，且測試全部通過。 |
| 相關檔案 | `config.ts` 和 `env.ts`。 |
| 儘快處理 | 在 2026-08-21 17:00（UTC+8）前處理。 |

若沒有數據，不要捏造數據。改寫為可觀察的描述，或明確標示尚未量測。

## 6. 詞彙

### 6.1 保留原文的內容

下列內容通常保留英文，並使用反引號：

- 程式碼識別字。
- 指令和參數。
- 檔名和路徑。
- API 欄位和錯誤碼。
- 產品、協定和函式庫的正式名稱。

常見縮寫不必每次展開。若縮寫對目標讀者可能陌生，第一次出現時補上全名或中文定義。

### 6.2 刪除沒有資訊的語句

通常可刪除：

- 「其實」「基本上」「某種程度上」等不改變主張的填充詞。
- 「值得注意的是」等沒有指出具體風險的開場。
- 「希望這對你有幫助」等不影響交付的結尾。
- 「進行修改」「做出調整」等可直接改成動詞的名詞化句型。

若這些詞承載真實限制或語氣，不要機械刪除。例如，「目前只能基本完成查詢」中的「基本」太模糊，應改寫為已完成和未完成的具體項目。

### 6.3 不用開放式清單定義需求

規格、範圍和驗收條件應使用封閉清單。不要以「等等」「之類」或「包括但不限於」隱藏未定範圍。

說明性內容若只列例子，使用「例如」，並明確說明該清單是例子，不是完整範圍。

### 6.4 避免模糊代詞

「此」「其」「相關」「對應」的指向不清楚時，重複具體名稱。

- 差：完成後更新相關文件。
- 好：完成後更新 `center-registry/spec.md` 和 `P0_通用語言.md`。

## 7. 不確定性、證據與來源

### 7.1 使用一致的狀態標示

需要區分事實和推測時，使用下列標示：

| 標示 | 使用時機 |
|---|---|
| 已驗證 | 已用資料、測試或權威來源確認。 |
| 推測 | 有部分證據，但尚未驗證結論。 |
| 假設 | 為了分析或設計暫時採用。 |
| 待確認 | 缺少決策、資料或外部回覆。 |

不要在每個句子前加標籤。以段落、表格欄位或小節統一標示即可。

### 7.2 證據靠近主張

主張後直接附上來源、測試結果或檔案位置。不要把所有來源集中在文末，讓讀者自行比對。

若來源互相衝突：

1. 並列衝突內容。
2. 寫明各自來源。
3. 建立或連結待決問題。
4. 在決議前，不選擇其中一個寫成現行規則。

### 7.3 錯誤分析分開寫

錯誤分析至少區分：

1. **現象：** 實際觀察到什麼。
2. **證據：** 錯誤原文、log、重現步驟或測試結果。
3. **推測：** 可能原因。未知時，不要把標題寫成「原因」。
4. **下一步：** 要執行哪個檢查，及如何判斷結果。

原始錯誤訊息放在程式碼區塊中，不翻譯或修正文句。

## 8. 結構與排版

### 8.1 段落、列表和表格

- 一個段落只處理一個主題。
- 有先後順序時，使用有序列表。
- 並列 3 項以上且讀者需要逐項檢查時，使用無序列表。
- 比較多個對象的相同欄位時，使用表格。
- 不要為了看起來簡短，把連續敘述切成大量單句項目。
- 巢狀列表通常不超過 2 層。超過時，改用小節。

### 8.2 標題

標題應直接指出內容，例如「待確認問題」或「驗證結果」。避免「其他」「補充」「相關說明」等無法預測內容的標題。

### 8.3 標點和空格

- 中文使用全形標點：`，。；：！？（）「」`。
- 程式碼、指令、網址和路徑內使用原本的半形標點。
- 中文與英文或阿拉伯數字之間，通常加 1 個半形空格。
- 數字和英文單位之間加 1 個半形空格，例如 `64 GB`。
- 日期使用 `YYYY-MM-DD`。跨時區的時間要標示時區。
- 嚴格模式不要用分號連接多個完整命題。拆成句子或列表。

既有正式名稱或專案格式若有不同規則，以正式名稱和專案格式為準。

## 9. 各類文件的寫法

### 9.1 規格和業務規則

規格正文只描述目前有效的行為。至少要讓讀者找到：

- 適用條件和角色。
- 系統行為。
- 例外和邊界。
- 可驗證的驗收情境。
- 仍待確認的問題連結。
- 決策或來源連結。

不要在每一條現行規則後附上完整修訂故事。修訂原因和被取代規則應移到決策紀錄。相關分工詳見 [知識治理架構](knowledge-governance.md)。

若目前只有暫行做法，明確標示「暫行規則」，並連結尚未解決的問題。不要把待決內容寫成確定規則。

### 9.2 GitHub issue

issue 應讓讀者快速找到：

- 問題或要達成的結果。
- 為什麼要處理。
- 範圍和不在範圍內的內容。
- 完成後可驗證的結果。
- 已知限制和待確認事項。
- 規格、問題或來源連結。

不要用 issue 取代完整規格。不要把「釐清問題」和「實作功能」藏在同一個模糊標題中。

### 9.3 會議紀錄

把內容分成：

- 已確認決議。
- 事實和進度。
- 待決問題。
- 行動項目。
- 原始脈絡或附件。

「會中討論」不等於「已決議」。只有明確確認的內容才能進入決議區。

### 9.4 操作步驟

程序依序寫：

1. 前置條件。
2. 操作步驟。
3. 每個重要階段的預期結果。
4. 失敗時的停止條件或排查入口。

每個步驟以具體動詞開頭。一個步驟只包含一個主要動作。若動作可能造成資料遺失或不可逆結果，先寫警告，再寫操作。

### 9.5 Pull Request 和工作交接

先寫結果，再寫細節。至少說明：

- 改了什麼。
- 為什麼改。
- 如何驗證。
- 哪些內容沒有處理。
- 是否仍有風險或待決問題。

不要只列出執行過的指令。讀者需要知道指令結果和結論。

### 9.6 程式碼註解

註解優先說明限制、原因或不明顯的決策。不要逐字重述程式碼。

- 差：`// 將 i 加 1`
- 好：`// 第一列是標題，資料從第二列開始。`

註解語言和術語依該 Repo 的既有慣例。

## 10. 警告與提示

使用下列等級：

| 等級 | 使用時機 |
|---|---|
| 警告 | 動作可能造成資料遺失、安全事件或難以回復的結果。 |
| 注意 | 動作可能失敗或造成可回復的錯誤。 |
| 提示 | 補充能降低理解成本的資訊。 |

警告必須放在危險動作之前。第一句先寫後果：

> **警告：** 強制推送會覆寫遠端歷史。執行前，先確認沒有其他協作者依賴該分支。

不要使用圖示或醒目格式代替具體後果。

## 11. 改寫範例

### 11.1 把現行規則和歷史分開

不建議：

> 系統原本在送出時就生效，後來 8 月 13 日會議認為應該看公文日期，所以現在原則上會依照日期處理，但有些舊資料可能還是不同，這部分之後再確認。

建議：

> **現行規則：** 系統依公文的生效日期變更狀態。
>
> **待確認：** 舊資料是否適用相同規則，尚未確認。
>
> **決策來源：** 2026-08-13 會議決議。

### 11.2 保留不確定性

不建議：

> 匯入失敗是第三方 API 不穩定造成的。

建議：

> **現象：** 10 次匯入中有 3 次逾時。
>
> **推測：** 第三方 API 的回應時間可能造成逾時。目前尚未排除本地端連線問題。

### 11.3 寫清楚待辦

不建議：

> 處理人員資料的相關問題，並視情況更新文件。

建議：

> 比對 `staff-management/spec.md` 和 `person-database-comparison/spec.md` 的身分證號歸戶規則。若兩份規格衝突，建立待決問題。決議後，再更新兩份規格。

### 11.4 不讓短句改變原意

原文：

> 若補習班尚未登載復辦公文，且停辦期限將在 30 天內屆滿，系統應顯示提醒。

錯誤改寫：

> 停辦期限將屆時，系統顯示提醒。

正確做法：

> 保留原句。拆除任一條件都會擴大提醒範圍。

## 12. 本指南不能解決的問題

本指南只能改善表達方式。它不能：

- 把未決事項變成已確認規則。
- 判斷互相衝突的來源何者正確。
- 補出缺少的業務知識。
- 讓沒有驗收方法的需求自動變得可驗收。
- 取代規格、問題和決策的治理流程。

遇到這些情況時，不要只潤飾句子。應建立待決問題或指出缺少的證據。治理方式見 [知識治理架構](knowledge-governance.md)。

## 14. 維護方式

本文件是跨專案文件類型的共同正典。修改時：

1. 以真實的誤讀案例說明要解決的問題。
2. 確認新規則不會刪除必要精度。
3. 更新受影響的正反例。
4. 若變更會改變要求強度或文件責任，另建決策紀錄。
5. 再評估是否需要更新 `AGENTS.md`、範本或 Skill。

不要因單一文件的特殊格式，擴大本指南的共同規則。特殊格式應留在該文件的範本或流程中。
